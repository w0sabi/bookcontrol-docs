Ziel: lauffähiger Prototyp mit funktionierendem Onboarding, modernisiertem UI und ohne die bekannten „komischen Bugs". Details und Belege zu allen Punkten in [Audit September 2026](/project/audit-2026-09).

## Leitplanken

- Das Design-Fundament (Tokens, shadcn, App-Shell) wird **behalten und ausgebaut**, nicht neu gebaut. Modernisierung = konsistente Anwendung + Politur, nicht Rewrite.
- Sicherheitsfixes K1–K5 sind Prototyp-Blocker, weil sonst kein Share-Link an Externe gehen darf.
- Strukturelle Datenmodell-Umbauten (tenant_id-Spalten überall, JSONB→Tabellen, FK auf festival_id) sind **nach** dem Prototyp dran.

## Phase 1 — Onboarding entsperren (17.–19.09.) ✅ umgesetzt 16.09.

Ohne das ist die App für neue User unbenutzbar; alles Weitere baut darauf auf.

- [x] `handle_new_user`-Trigger: neuer User wird **Admin seines eigenen Tenants**; eingeladene User treten via `app_metadata` (nur Service-Role) dem Tenant des Einladenden bei. Migration `20260916211000_owner_admin_onboarding.sql`.
- [x] **K1 vorgezogen** (Voraussetzung für Owner-Admin): Legacy-`FOR ALL is_admin`-Policies gedroppt, tenant-scoped Write-Policies + tenant-gescopte Rollen-/Member-/Invite-/Profil-/Signatur-Policies. Migration `20260916210000_tenant_scoped_write_policies.sql`.
- [x] `addFestival`: DB-Insert zuerst, Fehler werfen statt still verschlucken; Anlage blockiert bis `tenantId` geladen ist. Festival-IDs jetzt `crypto.randomUUID()`.
- [x] `invite-user` repariert: Rolle validiert, Tenant des Einladenden via `app_metadata` an den Trigger übergeben, keine doppelte Rollen-Zeile mehr; Rollen-Fetch im Frontend deterministisch (neueste Zuweisung gewinnt).
- [x] **Onboarding-Wizard** (`src/components/onboarding/`): First-Run-Flow bei fehlendem Profilnamen und/oder leerer Festival-Liste — Profil-Schritt → „Erstes Festival anlegen" (nur für Admins; eingeladene Nicht-Admins in leerer Organisation sehen einen Hinweis-Screen). Vollständig über i18n-Keys (EN + DE).
- [x] Nebenbei: Default-Sprache auf **Englisch** umgestellt (Owner-Entscheidung).
- [x] Migrationen deployed (Migrationshistorie musste vorher per `migration repair` auf die lokalen Dateinamen umgebucht werden — Lovable hatte abweichende Versionsnummern registriert), `invite-user` deployed.
- [x] **End-to-End-Test gegen die Remote-DB: 17/17 bestanden** — frischer User bekommt Admin + eigenen leeren Tenant, sieht 0 Festivals, kann eines anlegen und sieht es danach; Cross-Tenant-Lesen/-Schreiben blockiert; Invite über die echte Edge Function: Invitee landet im Tenant des Einladenden mit korrekter Einzelrolle, ohne Zusatz-Tenant, und sieht dessen Festival.

**Befund aus dem Test (16./17.09.):** Der öffentliche Signup-API-Endpunkt ist serverseitig NICHT deaktiviert (Invite-only war bisher nur UI-Kosmetik); er scheitert aktuell nur zufällig am Bestätigungsmail-Versand. `enable_signup=false` steht jetzt in `config.toml`, aber der Push wurde mit 403 abgelehnt — **Owner muss einmal im Dashboard deaktivieren**: Authentication → Sign In/Up → „Allow new users to sign up" aus.

**Entscheidung (17.09.):** `app_metadata` ist beim Signup-Trigger noch nicht gesetzt (GoTrue merged nach dem Insert) — die Tenant-Zuordnung von Invitees macht daher die `invite-user`-Function explizit per Service-Role (Rolle ersetzen, Membership umhängen, Auto-Tenant löschen).

**Entscheidung (16.09.):** Statt `is_admin()` tenant-bewusst umzubauen, wurden alle Admin-Policies mit einem zusätzlichen Tenant-Match versehen — kleinerer Eingriff, gleiches Ergebnis; `email_log`-Admin-SELECT (ohne Tenant-Bezug) bleibt als Phase-2-Punkt (K4-Umfeld).

**Bekannte Lücke für Phase 2:** `invite_links` hat weiterhin eine anon-SELECT-Policy (`is_active = true`) — gleiche Klasse wie K2, wird dort mit behoben.

## Phase 4 — UI-Modernisierung (gestartet: Design Guidelines beschlossen, Umsetzung auf Branch `redesign`)

Reihenfolge: erst gemeinsame Bausteine, dann Seiten in Nutzungs-Reihenfolge. Verbindliche Grundlage: [Design Guidelines](/design/guidelines).

- [ ] **Token-Ebene**: `--bc-*`-Variablen, Light als Default, Navy & Ice, 4 Status-Familien.
- [ ] **Gemeinsame Bausteine**: `PageShell`/`PageHeader`-Pattern; Skeleton-Loading- und Empty-State-Komponenten; Topbar auf `ui/`-Komponenten umbauen (Focus-Rings, a11y); Sonner-Theme-Bug fixen (an eigenen `ThemeContext` koppeln); doppelten `Toaster` entfernen.
- [ ] **Design-Politur** auf Token-Basis: Hex-Duplikate eliminieren (v. a. `BudgetExport`), fixe Pixelbreiten durch responsive Maße ersetzen, Z-Index-Ebenen konsolidieren.
- [ ] **Seiten modernisieren** (rohe `<table>`/`<button>` → shadcn, Loading/Empty/Error-States, PageHeader), priorisiert nach Sichtbarkeit: Dashboard (Index) → Bookings → Offers → Contracts → Riders → Timetable → Budget → Contacts → SocialAssets → ProcessMonitoring → Settings.
- [ ] **Monolithen nur so weit zerlegen, wie fürs Restyling nötig** (Timetable 1923 Z., Budget 1581 Z., Contacts 1302 Z.); vollständiges Refactoring nach Prototyp.
- [ ] **Public-Seiten**: gemeinsames, schlankes Public-Layout (Offer/Contract/Rider/Timetable/SocialAsset) — das sehen Agenturen zuerst.
- [ ] **Sprache: Englisch als Prototyp-Standard.** Beim Umbau jeder Seite alle hart codierten Strings (v. a. deutsche Toasts, Auth, Public-Seiten) durch i18n-Keys mit gepflegten `en`-Werten ersetzen. Deutsch wird danach durch reines Auffüllen der `de`-Sektion in `translations.ts` ergänzt — keine Komponentenänderungen mehr nötig.
